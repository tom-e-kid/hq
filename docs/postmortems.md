# 失敗談集 — hq plugin 開発の落とし穴

本書は規範文書ではない。設計原則の判定（`docs/design.md` § 設計原則）で言う「情報」であり、ハーネスのどの層にも属さず、監査対象にもならない。目的は 2 つ: 開発中に同じ落とし穴へ向かったとき参照できること、そして追って開発とは別に読み物として編纂するための素材を、事実と数字ごと保存しておくこと。

ここに載る事実と数値は、この plugin に至るまでの開発（別の repository で行われ、ここには履歴が無い）と、telemetry sink（`~/.hq/stream.jsonl`）から取っている。**一次ソースの多くはこの repository には無い** —— 数値は確定日とともに記してあるので、疑う側はその日付の記録に当たることになる。

## 1. 品質を上げるつもりで、工程を監査していた

**何が起きたか。** 以前の設計は「LLM の振る舞いを信じない」前提で、工程の形を強制するハーネスを組んだ。gate・機械の検査群・記録義務はすべて、工程成果物（計画書・決定記録・貼り込み）の形を検査していた。29 run の運用で機械 gate が検出した欠陥は 1 件。成果物の質に効いた検出はすべて「書いた本人でない当事者が、主張を数え直した」ことから出ていた（出所別: 第三者レビュー 35 / 実装者の自己報告 9 / 抜き取り検査 3 / 機械レール 1 / 振り返り 1。2026-08-10 確定）。同じ期間、外部レビュア（Copilot）は consumer repo の 3 PR で、plugin が「自分が検出する」と宣言していたクラスの欠陥を 2 件拾った。plugin は 5 倍の件数の指摘を出しながら、その 2 件を両方外した。

**なぜ起きたか。** 工程の形は決定可能で、検査しやすい。品質は決定不能で、検査しにくい。検査は検査しやすい方に集まり、「検査が回っている」という感覚が品質の保証と混同された。さらに憲法の選抜規則「保証機構を持たない原則は書かない」が正しく働いた結果、当時保証機構を持たなかった品質は条文から消え、目標の筆頭が憲章に存在しないまま 29 run 走った。規則は正しかった。欠けていたのは品質の保証機構の方だった。

**教訓。** 質を測りたければ、系の外に採点者が要る。自己申告の緑は何も保証しない。

## 2. 散文の規範は、明文でも飛ばされる

**何が起きたか。** 行動を指図する規範を prose で書き、それが守られる前提で設計を組んだ。実測: 同じ失敗クラスに規範を 3 箇所書いて 3 連続で再発（2026-08-06 確認）。終盤の run では、規範を書いた本人に相当する root agent が 1 run で 2 回、明文の規範に違反した（2026-08-11 確認）。2 件とも「規範は明文だが検査面が無い」箇所で起き、機械が見ていた面は同じ run で 0 落ちだった。

**なぜ起きたか。** prose への追記は、書いた瞬間に仕事をした感覚を生む。しかし読む面・検査する面が無い文は、運用上は存在しないのと同じになる。

**教訓。** 保証を散文に担わせない。ある一文を書いてよいかは「その文が守られることを設計が当てにしているか」で決まる。当てにしているなら、その保証は機械の検査か独立の検証者に移す。

## 3. 台帳が作業を駆動し始める

**何が起きたか。** 検出のたびに issue を起票し、対応キューで消化順を管理した。実測: ある期間の 8 run のうち、挙動が変わったのは 2 本のみ。残りは規範の追記 4 本と、その後始末 2 本だった（2026-08-06 の運用改定の根拠）。作り直しの時点で open issue は 36 件に達しており、全件 close して backlog ゼロから再出発した（2026-08-11）。

**なぜ起きたか。** 起票は検出の証明として機能し、台帳は消化の義務に変わる。義務は実測と無関係に作業を生む。さらに古い issue は当時の語彙で書かれているため、後から読むこと自体が古い設計の枠を新しい設計に持ち込む行為になる。

**教訓。** 追加・対応は実測が必要性を示した時に行う。台帳は持ち越さない。close は消去ではなく、closed issue は検索可能な先行情報として残る。

## 4. dogfooding の対象 repo が、指標を決めてしまう

**何が起きたか。** telemetry に貯まった 33 run のうち 29 run は plugin 自身の repo のものだった。この repo の成果物は工程成果物（規範文書・script・契約）であり、工程成果物向けの検出装置はここでは機能して見える。コード成果物へのカバレッジがゼロであることは、consumer repo で運用するまで指標に一度も現れなかった。

**教訓。** 指標を信じる前に、評価環境の分布を測る。

## 5. 収率を別の母集団に適用する

**何が起きたか。** 「この repo の prose diff で Critical 0 / High 2」という実測を根拠に、レビュアを検証構成から外した。しかしその収率は markdown の diff のもので、それをコードの diff に適用した。結果としてコード検証の空白が生まれ、外部レビュアがちょうどその空白を刺した。

**教訓。** 収率は diff profile（コード / 散文 / 混在）別に測り、profile をまたいで流用しない。

## 6. 飽和した指標を成功と読む

**何が起きたか。** レビューの first-pass 率が 29/29 = 100% だった。「一度も差し戻していない」は品質の証明ではなく、差し戻す主体が機能していないことの警報だった。指標の reader 自身が「目標でなく警報として読め」と印字する状態が続いた。

**教訓。** 指標が一方に張り付いたら、達成ではなく観測面の故障を疑う。

## 7. 学習の出口が一本しかない

**何が起きたか。** run を跨ぐ学習の唯一の経路を「plugin 改善の findings」に一本化していた。その結果、consumer repo の 3 run が恒久的に残したものは plugin への改善提案 14 件のみで、対象 repo 自体についての学び（どこで失敗しやすいか）は構造上どこにも出力できなかった。次の run は前の run の教訓を知らずに走った。

**教訓。** 学びの出口は学びの種類ごとに設計する。今の形では出口が 2 つに分かれている —— plugin への改善は findings と外部残存の記録へ、対象 repo についての学びは `.hq/knowledge.md` へ。

**ただし後者は機械化されていない。** run を跨いで agent に届く経路は注入 1 本だけで、注入されるのは `inject.sh` の `FILES` が名指すファイルである（§ 入力の統治 は `docs/design.md`）。**外部残存の記録は読み返されない** —— それは telemetry であって注入の対象ではなく、そこから学びを取り出して `.hq/knowledge.md` に書くのは人の仕事である。この項の欠陥は出口を作ったことで半分だけ閉じた。

## 8. 中身を廃止しても、機構だけが残る

**何が起きたか。** 規範文書から section を抽出し、束ね、byte 単位で注入を検査する機構があった。この機構が重厚だったのは、規範散文そのものが大部だったからである。作り直しの初期案は、中身（散文規範）を廃止した後もこの抽出機構を持ち込みかけた。指摘を受けて数え直すと、module 横断で注入すべき共有規範は新しい設計にはほぼ存在せず、機構は「ファイル全文の注入 + hash 一致の検査」まで畳めた。

**教訓。** 機構を引き継ぐ前に、その機構が存在した理由がまだあるかを問う。機構だけが残ると、それを埋める中身が再び増える。

## 9. 緑のテストと、効いているテストは別物

**何が起きたか。** 今の実装の最初の script（60 検査）を書く過程で、テスト自身の欠陥が 2 件見つかった。どちらも全検査が緑の状態で潜んでいた。

1 件目。`duration_s is a number, not a string` という名前の検査が、実際には値しか見ていなかった。script を変更して値を文字列として出力させても、この検査は通り続けた。名前が主張する性質を検査していない、いわゆる vacuous-test である。

2 件目。bash 4.0 以降の構文を列挙して照合する掃引で、正規表現が 12 項目のうち 2 項目（行頭の `mapfile` と、直後が空白でない `wait -n;`）に一致していなかった。列挙した構文をわざと仕込む手作業の試行で初めて分かった。

**なぜ起きたか。** テストは、書いた本人が「こう動くはず」と思った通りに書かれる。その思い込みが誤っていた場合、テストは思い込みごと固定される。緑は「期待どおり」を意味するのであって、「期待が正しい」ことは意味しない。

**教訓。** 検査を書いたら、検査対象をわざと壊して赤くなることを確かめる。列挙を持つ検査には、列挙した各項目を含む fixture を用意して、照合が全項目を拾うことを常設の検査にする。手作業の試行では、次に列挙が増えたときに同じ穴が空く。

## 10. 測り方が、失敗条件を打ち消す

**何が起きたか。** bash 3.2 で使えない構文を調べるため、`bash -c '...'` で 10 種類を試し、「どれも停止する」と結論して表にまとめた。この結論は誤りだった。同じ構文を script ファイルとして実行すると、shell は停止せず、標準エラー出力にメッセージを書いて実行を続け、間違った値のまま進む。

この違いは設計判断を変えた。「停止する」なら、テストを走らせれば必ず気づく。「停止せず値だけ狂う」なら、テストが到達しない経路では誰も気づかない。誤った前提のもとでは「構文の列挙は不要」と判断していたが、実測の訂正後は列挙による掃引を併用する構成に変えた。

**なぜ起きたか。** 確認が手軽な形（コマンド 1 行）と、実際の実行形態（script ファイル）が違っていた。手軽な形のほうが、たまたま失敗を目立たせる挙動をしていた。

**教訓。** 挙動を確かめるときは、本番と同じ形で実行する。対話で 1 行流して得た結論は、その 1 行という文脈込みの結論である。

## 11. 原則の名前で、やるべきことを先送りする

**何が起きたか。** 記録 script の `repo_slug`（記録の `repo` 項目を決める関数）の異常系を未検査のまま残し、「追加は実測で決める」という設計原則を根拠に挙げた。指摘を受けて確かめると、その原則は検証者や指標といった**機構を足すかどうか**の規則であって、既に書いた分岐の検査を先送りする根拠ではなかった。原則の適用範囲を取り違えていた。

しかも対象は基盤だった。`repo` は全記録行に付き、指標の母集団を切り、外部残存の注入対象を選ぶ。誤っても行は正しい形のまま出るので、下流のどこも気づかない。検査を 6 件足すのに要したのは 30 行程度だった。

**なぜ起きたか。** 自分の作業を減らす方向の解釈は、それを裏づける原則が手元にあると通りやすい。さらに、この件は「足りないものとして再掲する」形で 2 回言及していた。認識はしていて、行動だけが伴っていなかった。

**教訓。** 原則を根拠に何かをしないと決めたときは、その原則の適用範囲を読み直す。同じ欠落を 2 回書き出しているなら、それは保留ではなく先送りである。
