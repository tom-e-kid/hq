# hq plugin 設計

**どの module が既に在るかは、この文書に書かない。** 書けば module を 1 つ足すたびに手で直す行になり、実際に何度も直してきた。**実装を数えた結果は契約ではない** —— この文書が持つのは契約だけである。今どこまで出来ているかは `ls plugin/commands/` が答え、まだ無いものは § 残っているもの が名指す。

## 0. 要旨

hq は、AI エージェントによる開発サイクル（計画 → 実装 → 検証 → 出荷 → 学習）を、7 つの独立したモジュールと 1 つのオーケストレータで組み立てる plugin である。

設計の中心は 2 つある。第 1 に、ハーネスは LLM を制限するためではなく、目的に対する力を引き出すために使う。第 2 に、品質は工程の形を検査して保証するのではなく、出荷前に成果物の主張を検証し、出荷後に外部レビュアが見つけた欠陥を記録することで保証する。

標語: 工程を監査するのではなく、主張を検証する。

## 1. 用語

本文書で使う、この plugin に固有の語をここで定義する。一般的な開発用語（PR、diff、hash、schema など）は含めない。

**構造**

| 語 | 意味 |
|---|---|
| ハーネス | エージェントを取り巻く機械的な枠組みの総称。gate・注入・記録など、エージェント自身の判断の外側で決まっている仕組みを指す |
| 層 1 | 入力の統治のうち、機械が強制する部分。決定可能な述語だけを置く（§ 入力の統治） |
| 層 2 | 入力の統治のうち、情報を渡したことを機械が保証する部分。使い方は指図しない（§ 入力の統治） |
| 柱 A | 出荷前の検証。書いた本人ではない当事者が、成果物の主張を検証する（§ 出力の検証） |
| 柱 B | 出荷後の測定。外部のレビュアが後から見つけた欠陥を、クラス別に記録する（§ 出力の検証） |
| module | 単独で機能する基礎単位。7 つある（§ モジュール構成） |
| orchestrator | module を順に呼ぶ調整役。`hq:loop` がこれにあたる |
| 述語 | 真偽の 2 値で答えが出る条件。**決定可能な述語**とは、そのうち機械が実行すれば必ずどちらかに定まり、解釈の余地が無いものを指す（例: checkbox が全部埋まっているか）。文法用語の述語とは無関係 |
| gate | 条件を満たさなければ次に進ませない、機械的な検査 |
| 契約（contract） | module が守ると宣言する入出力の約束。gate の検査と注入の保証もここに含まれる |
| 面 | ある性質を観測または検査できる場所。「検査面が無い」は、違反が起きても気づける場所がどこにも無い状態を指す |

**成果物と検証**

| 語 | 意味 |
|---|---|
| 主張 | 成果物が暗黙に述べている内容。「このテストはこの性質を検査している」「この数はこう数えた」「この変更は既存の単一ソースと整合している」など。柱 A の検証対象 |
| findings | 検証者や外部レビュアが出した、個々の指摘 |
| disposition | findings 1 件ごとの処置判定。fix now（すぐ直す）、defer（先送りする）、reject（対応しない）の 3 値 |
| consequence | 指摘された欠陥が実際に引き起こしうる帰結。triage はこれの有無で処置を決める |
| diff profile | 変更内容の分類。コード / 散文 / 混在の 3 種。検証者を選ぶときの入力になる |
| 収率 | ある検証者や機構が、実際にどれだけ欠陥を検出したかの実績。「profile 別の収率」は、コード / 散文 / 混在それぞれでの実績を指す |
| 単一ソース | ある事実や規則の定義を置く唯一の場所。同じことが 2 箇所で定義されると食い違い（drift）が起きる |
| 宣言クラス | loop が「この種類の欠陥は自分が検出する」と宣言している欠陥の種類。一覧は検証者の定義が持つ（§ 出力の検証） |
| 外部残存 | loop が出荷した後に、loop の外にいる独立レビュアが見つけた欠陥。柱 B が記録する。ここでの「loop の外」とは、loop がその相手を呼び出しておらず、出てくる指摘の内容にも loop が関与できないことを指す（ユーザの PR レビュー、ユーザが起動する外部レビューツール、Copilot が使える repo ではその PR レビュー） |
| 工程成果物 | 計画書・決定記録・レビュー報告など、開発の過程で作られる文書。利用者に届くコードやドキュメント（成果物）と区別するために使う |

**実行と記録**

| 語 | 意味 |
|---|---|
| run | 計画から出荷までの 1 サイクル分 |
| 注入 | subagent の起動時に、決められたファイルの全文を prompt へ貼り込むこと（§ 入力の統治） |
| implement / overhead | `hq:implement` の所要時間 / それ以外の module の所要時間の合計 |
| micro-fix | triage が fix now と判定した小さな修正を、計画からやり直さずに `hq:implement` へ直接戻す経路 |
| red-on-revert | 検査が本当に効いていることの確認方法。違反を意図的に入れると必ずテストが落ちることを確かめる |
| telemetry | run 中の出来事を 1 行ずつ記録したもの。集約先は `~/.hq/stream.jsonl`（§ 記録と評価指標） |

## 2. 目標

ユーザが確定した 4 項。

1. **アウトプットの質を、安定して高い水準に保つ。** 保証機構は外部残存の記録（§ 出力の検証の柱 B）。
2. **1 サイクルにかかる時間を可能な限り抑える。** 指標は overhead/implement 比（§ 記録と評価指標）。
3. **ハーネスは LLM を制限するためではなく、目的に対する力を引き出すために使う。** 具体形は § アーキテクチャ。
4. **Sandbox とポータビリティの優先度は下げる。** ただし Claude Code Plugin の標準（plugin.json / hooks / agents / skills の構成）には準拠する。`gh` CLI への依存は許容する。

## 3. 設計原則

**シンプルかつ明瞭に書く。**
prose も script も、読んだ人が挙動を説明できる簡潔さを保つ。複雑さが増える変更は、その複雑さと引き換えに何の保証や機能が得られるのかを説明できなければ入れない。既存の実装を参考にするのはよいが、参考は移植ではない。この plugin の語彙や構造に合わないものは書き直す。

**すべての script はテスタブルにし、テストコードを付ける。**
script 1 本に対して test ファイル 1 本を並べる（例: `foo.sh` と `foo.test.sh`）。「すべての script に test が付いていること」自体が決定可能な述語なので、テストスイートが機械的に検査する。gate の述語は red-on-revert で確かめる。

**一覧を照合する検査は、一覧を網羅した fixture を持つ。**
「既知のものを列挙して照合する」形の検査（構文の掃引など）は、列挙が実態から外れても緑のままになる。そこで、列挙した各項目を 1 行ずつ含む fixture を置き、検査がそのすべてを拾うことを確かめる。これは決定可能なので機械が検査する。

**利用者に見える出力も検査の対象にする。**
`--help` のような出力は、実装から自動で導かれるとは限らない。ここでは、help が全 kind と全ての受理値を含むことを検査する。help をヘッダーコメントの行範囲から切り出すような実装は、ヘッダーが伸びた時点で文の途中で切れる —— 出力そのものを見る検査でしか捕まらない。

**script は bash 3.2 で動く。**
macOS が `/bin/bash` に載せているのは 2007 年の 3.2 であり、ライセンスの都合で更新されない。一方、開発機の PATH では Homebrew の 5.x が先に来る。`#!/usr/bin/env bash` はどちらも拾うため、**手元で通って利用者の環境で壊れる**差が生まれる。使えない構文の一覧は掃引の正規表現（`sweep.test.sh`）が単一ソースで持ち、その全項目を含む fixture が正規表現と一致することを検査する。連想配列（`declare -A`）、`mapfile` / `readarray`、`${var^^}`、`local -n` などが該当する。ここに一覧を書き写さないのは、2 本目の一覧を機械が照合できないためである。

**壊れ方は「落ちる」ではなく「黙って値が狂う」である。**script ファイルとして実行した場合、未対応の構文に当たっても shell は停止しない。stderr にエラーを書いて実行を続け、間違った値のまま進む。`declare -A` が失敗した変数は通常の添字配列になり、添字が算術式として評価されるため文字列キーがすべて 0 に潰れて互いを上書きする。`${v^^}` は空を返す。`mapfile` は「command not found」を出して配列が空のままになる。`bash -c` では即座に停止するので、対話で確かめると停止する側の挙動を見てしまう点に注意する。

保証はテストが持つ。**単独では十分な検査が無いため、3 つを併用する。** それぞれの盲点は次のとおり。

| 検査 | 捕まえるもの | 盲点 |
|---|---|---|
| 再実行 | テストが検証している挙動を変える構文。テストスイート自身と対象 script を `/bin/bash` でも走らせ、同じ結果になることを見る | テストが到達しない経路 |
| stderr が空 | 結果を変えずにエラーだけ出す構文。古い bash での正常系実行が何も出力しないことを見る | 到達しない経路、エラーを出さない構文 |
| 構文の掃引 | 到達しない経路にある構文。既知の 4.0 以降の構文を全 script から grep する | 一覧から漏れた構文 |

掃引の一覧は原理的に不完全である。だから掃引だけに頼らず、上の 3 つを併用する。古い bash が無い環境では、検査を飛ばしたことをテスト出力に明示する。

**保証を置ける場所は 2 つしかない。機械の検査（層 1）と、独立した検証（柱 A・B）である。散文は保証を持てない。**
文書に一文を足すときは、その文が守られることを設計が当てにしているかを問う。

- 当てにしていないなら書いてよい。それはタスク定義か情報であり、仮に守られなくても、保証は gate や検証者が別に持っているからである。module の指示文はここに入る。
- 当てにしているなら書けない。守られなかったことに誰も気づかないまま、保証があるつもりになるからである。この場合は保証を層 1 の述語か柱 A・B の検証に移す。移せないなら「この保証は無い」と明記する。

**機構は、効かなくなったことが分かる形で作る。**
gate・hook・検証・記録のように「気づくこと」が仕事のコードは、普通のコードと壊れ方が違う。気づかなくなり、そのこと自体に誰も気づかない。テストは緑のまま、報告は「問題なし」のまま、通り抜けた欠陥だけが違う。

**検査が「実装したとおりに動くか」しか見ていないと、「実装しなかった経路」は誰も見ない。** 機構を書くときは次の 4 点を確かめる。

- **失敗と空の結果を区別する。** 空の出力に意味がある command は、終了コードも読む。`git diff` の失敗を空の diff と同一視すると、base の設定誤りが「変更なし」になり、検証がまるごと飛ぶ
- **検査できなかったことを、検査して問題なしと区別する。** できなかったことは必ず言う。JSON parser が無い環境で validator が黙って通ると、検証済みのファイルと見分けが付かない
- **書き手が取りうる経路をすべて覆う。** agent の tools を読み、どれが対象に届くかを問う。`Write` だけを見る hook は、同じ agent の `Bash` による書き込みを素通りさせる。覆いは tool の水準だけでなく、渡るパスの表記まで下りて確かめる
- **受領証と実体を区別する。** 「この検査が受理する最小の入力は何か」を問う。注入 block の digest 行だけを持つ prompt は、本文を 1 行も含まずに gate を通りうる

**宣言した挙動には検査面を付ける。**
ヘッダや文書に書いた終了コード・分岐・依存の有無は、書いた時点で真でも、検査が無ければ次の変更で偽になる。到達しにくい分岐は、差し替え口を設けてでも叩く（`HQ_PYTHON` / `HQ_DIGEST` / `HQ_SINK`）。テスト用の口を足すことは、宣言したまま検査しない状態より安い。

**同じ事実を 2 箇所に書いたら、照合を機械に持たせる。**
修正のときは「他にどこで同じことを言っているか」を必ず探す —— 1 箇所を直しても同じファイルの別の箇所が残れば、それが同じ欠陥の 2 件目になる。ただし**照合できるのは機械が抽出できる形だけ**である。自然言語の言い回しを列挙して禁じる検査は書かない —— 列挙が原理的に不完全なので、「何かを検査している」という誤った安心だけが残る。照合できないなら、再記述そのものを削る。

**追加は実測で決める。**
検証者・注入する情報・指標・数値目標は、実測（主に柱 B の記録）が必要性を示した時に足す。「あれば便利そう」では足さない。

ただしこれは**機構を足すかどうかの規則であり、既に書いた分岐をテストするかどうかの規則ではない**。存在する分岐を未検査のまま残すのは保留ではなく、単に穴である。とくに、出力が不正でも形としては正しく見える箇所（記録の項目値など）は、間違っても下流が気づかないので、実害が出るのを待たずに検査を書く。

## 4. アーキテクチャ

入力は 2 つの層で統治し、出力は 2 つの柱で検証する。

### 4.1 入力の統治 — 層 1 と層 2

**層 1 — 機械が強制する。**

置けるのは決定可能な述語だけである。例: PR を作る前に checkbox が全部埋まっているか、注入された内容が現行のファイルと一致するか、diff profile がどれか。答えが解釈に左右されるものは置かない。解釈を機械に判定させると誤検知が生まれ、run が止まるからである。

**層 2 — 情報を渡したことを機械が保証する。**

subagent の起動時に、決められたファイルの内容を prompt へ貼り込む。これを注入と呼ぶ。

- 何を注入するかは、ファイルの一覧として持つ。**一覧の単一ソースは `plugin/scripts/inject.sh` の `FILES` であり、この文書はパス名を持たない。** 注入を増やすとはその 1 行に足すことで、他に switch は無い。**run を跨いで agent に何かを伝える経路は、これ 1 本しかない。** 機械が書き出す 2 本目を最初に置いたが、中身を持たないまま残ったので外した。
- **この経路は拡張点であり、plugin のどの保証もその中身に依存しない。** 層 2 が保証するのは渡したことであって、中身があることではない。**空が既定の状態**で、module の入力は repo の状態（branch・diff・base）から導出できる（§ モジュール構成）。したがって「空だから出来が悪い」という説明は成立しない —— 空は未設定であって、欠落ではない。
- **repo の文書が既に述べていることを、ここに書き写さない。** 二重記述は必ず腐り、腐っても誰も気づかない —— この repo は実際に、`AGENTS.md` と同じ事実をここに置いて、片方だけが古くなる形を出している。書くのは、repo の文書を読んでも分からない事実に限る。
- **注入するのは常にファイルとする。** telemetry を注入器に直接読ませない。telemetry は全 repo 共有の追記ログであり、有用な注入を作るには repo・種類・期間での絞り込みが要る。それは下の「全文をそのまま貼る」に反し、一致検査の対象も定まらなくなる。telemetry から作った注入が要るとなったときは、絞り込みと整形を先に済ませてファイルとして固定し、その結果を一覧に足す。これにより、どの要素にも同じ注入契約が等しく成立する。
- 注入はファイルの全文をそのまま貼る。必要な節だけを抜き出す加工はしない。
- 注入について機械が行う検査は 1 つだけである。prompt に貼られた内容が、現行のファイルと一致するかを見る。**実装は marker と hash の照合とする。** 注入器はブロックを marker で囲み（開始 1 行と、ファイルごとに 1 行）、末尾に本文から計算した sha256 を ASCII の 1 行として置く。gate はそれらの行が起動 payload にすべて含まれるかを見る。本文そのものを照合しない理由は実測にある —— payload は harness が符号化した JSON であり、その encoder は我々のものではない。非 ASCII を `\uXXXX` で出す encoder の下では、注入ファイルが日本語を含む時点で本文照合は毎回外れる。テストでは実際に、payload 中にファイルの生バイトが 1 つも現れない状態で marker と hash 行だけが一致することを確認している。
- **起動 gate は注入以外にもう 1 つの述語を持つが、それは注入の検査ではない。** 起動 prompt が run の作業ファイルの置き場を運んでいるかを見るもので、規定は § 作業ファイルの置き場（「agent には caller が渡す」）にある。同じ script が両方を担うのは、どちらも「caller が prompt に入れたはずのもの」を起動時にしか見られないからであり、2 つの述語は互いに独立に評価する —— 片方が判定不能でも、もう片方は黙らない。
- **この検査の保証には限界があり、それを明記する。** 照合できる行はすべて ASCII であり、本文が実際に届いたことの唯一の証拠である本文そのものは、encoder が書き換えうる。したがって marker と現行 hash を保ったまま、その間の本文だけを落とした prompt は検出できない。保証されるのは「何かが注入され、それが現行版で、正しい形をしている」ことであって、「全バイトが存在する」ことではない。本文照合を足せば閉じるが、上記の理由でそれは全 launch を止める。この穴は残したまま、ここに書く（§ 設計原則の「移せないなら『この保証は無い』と明記する」に従う）。
- **注入するファイルは、その repo で追跡する（git の管理下に置く）。** `.hq` を丸ごと無視すると、新しい clone や worktree に注入元が存在せず、注入は空のまま契約を満たす —— 渡す情報がゼロであることに、どの検査も反応しない。どのパスを追跡し、どれを無視するかは § 作業ファイルの置き場に定める。
- **一覧のファイルが存在しない場合は、内容が空であるものとして注入し、一致検査も「存在しない」状態に対して行う。** 存在しないこと自体は誤りではない。repo 固有の事実のファイルは人が置くまで存在しない。注入器はファイルを作らない —— 作ると「渡した事実を検査する」以上のことを始めてしまう。この規定により、新しい repo の最初の run でも層 2 の契約が成立する。
- どう使うかは LLM に任せる。機械が検査するのは、渡したという事実だけである。
- module をまたいで共有する規範のファイルは、中身が無いうちから用意しない。共有すべき情報が実際に生まれた時点で一覧に足す。逆に、必要な節だけを抜き出す仕組みが欲しくなるほど注入ファイルが育った場合は、散文が増えすぎたと判断する。

**層 2 が届くのは subagent の起動だけである。** root session が自分で読む文脈には、注入の一致検査に相当する面が無い。`hq:plan` は計画 gate（ユーザへの提示と go / stop）を持つため subagent を立てられず、注入器の出力を root が読む形になる。したがって `hq:plan` については「渡した事実」の保証が無い。これは § 設計原則の「移せないなら『この保証は無い』と明記する」に従って明記するものであり、module の定義にも同じことを書く。

層 2 に載らない情報は、ハーネスの一部ではない。単なる会話であり、監査の対象にしない。行動を散文で指図し、その遵守に保証を依存させる規範は、どちらの層にも置けない（§ 設計原則）。

### 4.2 出力の検証 — 柱 A と柱 B

**柱 A — 出荷前に、独立した検証者が主張を検証する。**

成果物の主張を、書いた本人ではない当事者が検証する。

- **検証者は変更ファイル単位で選ぶ。** 割り当ては `plugin/scripts/lib.sh` の `hq_verifier_for` が 1 箇所で持ち、呼ぶ側は自分で分類し直さない。PR 全体の profile は記録と収率の分類に使うものであって、検証者を選ぶ単位ではない。
- **初期の検証者は 1 種で、変更ファイルの全部に当てる。** 汎用のコードレビュー用 agent をもとに、この plugin の語彙で書き直す。**コードのファイルに限らないのは、`.md` だけを変える PR がその構成では一度も見られないまま出荷されるためである** —— 外部残存には、その形の PR から出た宣言クラス内の欠陥が実際に含まれている。
- 書き直しで引き継ぐのは 2 つ。構造上必要なコードを冗長と誤認しないための抑制リストと、検証者には実装側より弱いモデルを使わないという原則である。主軸には主張の検証を据える。ただし**探索の視野は狭めない** —— 主張の反証は指摘を採るかどうかの関門であって、どこを見るかの制限ではない。宣言クラスに当てはまらない欠陥は、クラスを付けずに出す。
- 検証者が 1 つも適用されないのは、diff が空のときだけである。その場合は「検証なし」と PR に明記する。
- 検証者を増やすのは、柱 B の記録が見逃したクラスを示した時だけである。増設時に変える箇所は `hq_verifier_for` の分岐 1 つに定まる。
- **findings は重み（`weight`）を持つ。値は high / medium / low の 3 つで、これは注意の順序ではなく disposition の入力そのものである。** 重みが答える問いは 1 つだけ —— この指摘を残したまま出荷できるか。high と medium が 1 件でも残る限り出荷できない。low は出荷を止めない。**重みを付けるのは検証者であり、triage は受け取るだけで書き換えない** —— 重みが判定の側で動かせると、費用の都合が重みの姿を借りて出口になる。
- **重みの存在と受理値は層 1 が保証し、重みの正しさには保証が無い。** `findings-gate.sh` が必須 field として検査し、受理値を enum で見る。付けた重みが妥当だったかは決定可能でないので、採点は柱 B が行う —— 外部レビュアが後から重大な欠陥として出したものを検証者が low と付けていれば、それがそのまま検証者の採点になる。
- **重み・費用・挙動接触は別の軸で、混ぜない。** 重みは出荷を止めるかを決める。費用は直すかを決める —— 限界費用がほぼゼロのもの（typo、1 行の書き換え）は重みと無関係に直し、low はどのみち走る修正 pass に相乗りする。挙動接触は再レビューを回すかを決める —— code の意味か、実行時に読まれる指示の意味を変えた修正だけが次の周を起こし、記録文書の修正・削除・typo は gate が通れば終わりである。この 3 つを 1 本にまとめると、軽い指摘が重い出口を強制するか、重い指摘が安さを理由に落ちるかのどちらかになる。
- **`id` は見つけた順とする。** 重い順にはしない（順序が判断になると、同じ diff で順が変わって再現性が落ちる）。**`id` は branch の中で、review の周をまたいで一意とする** —— 2 周目以降は前の周の続きの番号を採り、findings のファイルには追記する。書き換えない。これにより `<branch>#<id>` が branch の寿命のあいだ 1 つの指摘だけを指し、triage の記録が周をまたいで結合できる。
- **この一意性を保証するのは findings-gate の重複 id 検査であり、追記である限りそれで足りる。** ファイルを丸ごと書き直して番号を振り直した周は、同じ検査を通り抜ける —— **その形に対する保証は無い**（§ 設計原則）。
- **検証の深さは、対象の役割で傾斜させる。** 分類は `hq_classify_file` の code | prose に載せ、新しい分類は作らない。
  - **code** —— 全力。主張の抽出、実行による反証、機構のチェックリスト、抑制リスト、consequence 必須。
  - **prose の既定** —— 事実の照合。述べていることが、参照先・実装・記録と一致するか。
  - **挙動を指図する prose**（LLM が実行時に読む指示、人が従う手順）—— 1 段上げ、挙動読み（この文に従った者は何を間違えるか）と削除の目（この文が無ければ何が壊れるか）を加える。
- **指図か記録かの判別は検証者の判断であり、機械の述語にならない。ここに保証は無い**（§ 設計原則）。傾斜の根拠は、散文には実行という終点が無いことにある —— 1 文が 1 主張で、修正が新しい文を書くため、往復しても主張の母集団が縮まない。**この規定は repo 固有のファイル名を持たない。** plugin は複数の repo に入るので、どのファイルが指図かは repo ごとに違う。
- **2 周目以降の review は差分レビューとする。** 起動時に運ぶのは 3 つ —— 前の周の findings と triage の判定（`fix_now` は修正されたかを検証し、`reject` は再び出さない）、前の周の「崩せなかった主張」の一覧（修正が触っていない主張は再検証しない）、修正 pass の commit 範囲。全力で見るのは新しく書かれた分である。**これは同じ計器の再測定を省くだけで、独立した再検証ではない** —— 独立性は柱 B が持つ。
- **前の周の文脈が実際に運ばれたことに保証は無い。** 層 2 が保証するのは一覧に載ったファイルを渡した事実であり、周ごとに変わる文脈はその一覧に載らない（§ 入力の統治）。§ 設計原則 に従って、無いと書く。

**柱 B — 出荷後に、外部レビュアが見つけた欠陥を記録する。**

loop が呼び出しておらず、指摘の内容にも loop が関与できない独立のレビュアが、後から見つけた欠陥をクラス別に記録する。この仕組み全体のなかで、loop の外から採点される唯一の面である。

誰がレビュアになるかは repo ごとに異なる。ユーザ自身の PR レビュー、ユーザが起動する外部のレビューツール、Copilot の PR レビュー（利用できる repo の場合）などが該当する。柱 B が要求するのは特定のサービスではなく、上記の独立性だけである。

**手段は、次の 2 条件を満たす外部レビューであれば何でもよい。**

- **起動を loop 側が行えない。** ユーザだけが起動できる形であること。
- **検出範囲を我々が決めていない。** レビューの prompt を hq 側で書かない。焦点を指定する引数も、柱 B として使うときは渡さない。渡した時点で、我々が決めた範囲で我々を採点することになる。

条件を満たす手段の例は 3 つある。どれが使えるかは repo と環境による。

| 手段 | 起動 | prompt の出所 | 備考 |
|---|---|---|---|
| Copilot の PR レビュー | GitHub が PR に対して自動で行う | GitHub | 全 PR に自動で走るため分母が構造的に埋まる |
| `/code-review ultra` | ユーザのみ（plugin から起動できない） | Anthropic | Claude のクラウドレビュー |
| `/codex:review` | ユーザのみ（plugin から起動できない） | OpenAI | 別ベンダの別モデルであるため、Claude を使う柱 A とは検出の盲点がずれる |

Copilot が使える repo では最も望ましい。人手を介さず全 PR に走るので、記録の抜けが起きないためである。使えない場合は、ユーザが起動する 2 つで代替する。

**外部レビューを実施したかどうかも記録する。**
外部レビューが自動で走らない環境では、実行漏れが「指摘ゼロ」と区別できなくなり、分母が壊れる。そのため残存記録は、指摘の件数とは別に「外部レビューを実施したか」を持つ。この 2 つを組み合わせて、実施して指摘あり / 実施して指摘ゼロ / 未実施を区別する。指標を読むときは、未実施の PR を母集団から除く。

**頻度はコストで決まる。** 常時実施できるならそうする。できない場合は節目に絞り、script が入った PR を優先する（実測が無い profile がコードであるため）。間引いても指標は汚れない —— 上の区別が未実施の PR を母集団から除くためである。低下するのは測定の精度であって、正しさではない。

**hq の module や script は、外部レビューの CLI を呼ばない。** `codex` のようなレビュー用 CLI は PATH 上にあり、module から実行できてしまう。実行した時点でそのレビュアは loop の内側に入り、柱 B の測定手段ではなくなる。これは決定可能な述語なので、層 1 で検査する。テストスイートに、`plugin/` 配下の module 定義と script が外部レビュー CLI を起動していないことを確認する sweep を置く。

得られた数字は、次の 4 つの判断に使う。

1. 目標 1（質）の保証（第 1 条）
2. 柱 A に検証者を増やすかどうかの判断
3. triage の採点（「検出したが落とした」区分）
4. **素の LLM 指示と比べて loop に価値があるかの判断。この問いは閉じない。** loop が所要時間に見合う価値を持つかは、作ってからも常に開いたままの問いとして扱う。答えは印象で出さず、柱 B の記録と § 記録と評価指標の指標で出す。

記録の運用は次のとおり。

- `hq:archive` が merge 後に書く。merge した全 PR について必ず記録を残し、レビュアごとに 1 行とする（1 つの PR を複数のレビュアが見ることがあるため）。分母が欠けると指標として読めなくなるためである。
- 書く側に判断を負わせない。選別せずに全件記録し、解釈は読むときに行う。
- **記録は追記だけで、行を書き換えない。** 未実施として記録した後に外部レビューを実施することがあるため、読むときの規則で解決する。**その PR に `reviewed` の行が 1 つでもあれば、その PR はレビュー済みとして読む。** `not_reviewed` の行が意味を持つのは、その PR に `reviewed` の行が 1 つも無いときだけである。
- **クラスの語彙は、柱 A の検証者の定義（`plugin/agents/reviewer.md`）が単一ソースとして持つ。** 検出範囲の宣言と 1 対 1 で対応させ、記録 script の enum と一致することはテストが検査する。この文書は一覧を書き写さない —— 書き写した瞬間、照合できない 3 本目になる。

**2 つの柱に加えて、欠陥が現れる面が 2 つある。**

品質を持つのは 2 つの柱である（第 1 条・第 4 条）。ただし欠陥が最初に現れる面は 4 つあり、それぞれ違うものを見せる。柱を増やす話ではなく、**すでに存在している面を数えておく**という話である。

| 面 | そこで現れるもの |
|---|---|
| 柱 A（出荷前の検証） | 成果物が述べていることが成り立つか |
| 柱 B（出荷後の外部レビュー） | 同上を、loop の外にいる独立した目で |
| **説明** | 述べて**いない**こと —— 入力の出所、扱っていない状況、前提として置いている知識 |
| **実行** | 述べたとおりに**動く**か |

**説明の面は、module の使い方を一通り書いた時に現れる。** 読み手を想定して起動から成果物まで説明しようとすると、書いていない前提が書き手自身に見える。**ここで出るものは柱 A・柱 B の指摘と重ならない** —— どちらも書かれた主張を検証する仕組みであり、書かれていないことは視野の外に落ちるためである。

これは工程に置ける形をしている。**module を出荷する前に、起動から成果物までを一度説明として書く。** 次の module から実施する。

**実行の面は、その module を実際に使った時に現れる。** 定義の記述が正しくても、記述どおりに動くとは限らない —— hook が登録された形では起動しない、記録の値が経過時間でなくなる、diff の一覧に git の警告が混ざる、といった形である。説明では出ず、実行して初めて出る。**この repository ではこの面が作られない**（§ 残っているもの）—— 使うのは他の repository である。

### 4.3 作業ファイルの置き場 — `.hq/` と `~/.hq/`

作業する repo の側に置くファイルを、ここに定める。`.hq/` は当初「一時的な作業データ」の置き場として始まったため、寿命も共有範囲も違うものが同じ前提の上に積み上がっていた。

| パス | 中身 | 書く主体 | git |
|---|---|---|---|
| `.hq/settings.json` | script が読む設定。現在は base branch のみ | 人 | 追跡 |
| `.hq/knowledge.md` | その repo でしか成り立たない事実のうち、repo の文書からは読み取れないもの。**空が既定** | 人 | 追跡 |
| `.hq/pr.md` | その repo で PR 本文が従う形式。節の構成を再定義する形も、文体の指針だけを置く形も、その repo が決める。**無ければ既定の 3 節** | 人 | 追跡 |
| `.hq/xcodebuild-config.md` | その repo を `xcodebuild` で build し、simulator で起動する command。**Xcode の workspace / project が無い repo には無い** | `hq:xcodebuild-config`（利用者との対話で決めて書く） | 追跡 |

**このうちどれが注入されるかは、この表が決めない。** 層 2 の一覧は `inject.sh` の `FILES` が単一ソースで持つ（§ 入力の統治）。ここに `○` の列を置くと、同じ一覧が 2 箇所に分かれ、どちらが正かを機械が決められなくなる。

**この表の file は repo の事実であり、追跡する。** clone した全員と全 worktree に等しく効く必要がある。`.gitignore` は追跡する側を列挙しない —— 列挙すると、この表に行を足すたびに 2 箇所を直すことになる。

**simulator の選択（device 名と OS）だけは機械の側の事実で、厳密には repo の事実ではない** —— 入っている runtime は機械ごとに違いうる。それでも追跡側に置くのは、利用者が 1 人で機械を跨いだ運用が無く、home 側に置くと clone や worktree ごとに設定し直す形に戻るためである。機械ごとに runtime が違う運用が出た時点で、この行の置き場を home 側に動かす。

**run の作業ファイルは repo の中に置かない。** 計画書・findings・報告は run ごとの作業状態であって、その project の成果物ではない。置き場は home 側である。

| パス | 中身 |
|---|---|
| `<HQ_HOME>/stream.jsonl` | telemetry の sink。`HQ_SINK` は file 単位でこれを上書きする |
| `<HQ_HOME>/repos/<repo-key>/tasks/<branch-dir>/` | その branch の run の作業ファイル（`plan.md`・`findings.jsonl`・`reports/`・`directives/`・`checks.md`・`run_id`） |

**`checks.md` は、builder が足した検査を「どう壊して、どの赤を見たか」で残す記録である。** pass ごとに追記され、書き手の返答の checks: 行が数える単位は検査（個々の test case / assertion）であって、entry はその記録の粒度にすぎない —— 1 つの entry が複数の検査を記録しうる。数えるのはその pass が足した検査だけで、以前の pass の分は数えない。読み手は検証者で、vacuous-test の反証で記録された壊し方を対象の copy 上で再生する（tree は変えない）。網羅の保証は無い —— 「何が検査か」は決定可能な述語にならないため、§ 設計原則に従ってここに無いと書く。

**`directives/triage-<YYYY-MM-DD-HHMM>.md` は、triage が `fix_now` と判定した指摘の修正指示（directive）を、triage の pass ごとに 1 ファイルで置いたものである。** 書き手は `hq:triage`、読み手は `hq:implement` の micro route であり、1 ファイルがそのまま 1 回の micro pass になる。pass ごとに 1 ファイルとするのは `reports/` と同じ形で、「今回の pass の分」をファイル名が答えるためである。**置いた理由は、起動 prompt の中にしか無い directive が失われるからである** —— micro pass が途中で死ぬと消え、triage を再実行しても復元しない（判定済みの id は再判定されず、`triage-gate.sh check` も clean を返す）。件数を記録に載せる面ができるのも、ディスクに落としたことの効果である（§ 記録と評価指標）。

**この理由が成立するのは、書き出しが処置（disposition）の記録より前にある場合だけである。** 処置を先に記録すると、その 2 つの間で死んだ pass は「全件処置済み・directive 無し」で終わる —— 復元しない条件はそのまま効くので、ファイルを置いたこと自体が同じ喪失を 1 段手前で作り直すことになる。書き出しが先なら、そこで死んだ run には処置の行が無い。`triage-gate.sh check` がその指摘を未処置として名指し、triage の再実行が判定からやり直せる。**したがって順序は置き場の付随ではなく、置いた理由が成り立つ条件である。** 倒れた pass の書きかけは上書きしない —— pass ごとに 1 ファイルの規則のまま、次の pass は新しい timestamp で自分のファイルを書く。

**置き場のディレクトリを作ることは、`hq:triage` の側が持ち、`reports/` の側は持たない。** `hq_task_dir` は run の作業ディレクトリを導出するだけで、その下のディレクトリを作らない。これまではどちらの側も、書き込みが親ディレクトリを作ることに依存していた（`reports/` は作成の保証が無いまま報告が積まれている）。**保証を持つのが書き手である必要は無い。** `hq:triage` はたまたま自分で書くので自分で作るというだけであり、`reports/` の側も**置き場を導出しているのは書き手ではなく caller である** —— `hq:review` の § Context が `lib.sh` に問い、その値を起動 prompt に逐語で載せ、subagent（`agents/reviewer.md`）はそれを与えられた事実として使う（同じ節の後段「agent には caller が渡す」）。`hq:review` も `hq:triage` と同じだけ bash を打てるので、`hq:triage` に足したのと同型の 1 行を自分の手順に置けば、agent の散文を一切介さずに `reports/` を作れる。**したがってこの gap は塞げないのではなく、塞いでいない。** その上で**現時点で `reports/` の側に作成の保証は無く**、§ 設計原則 に従ってここに無いと書く。作成の段は、無ければ作るというだけのものであって、既に起きている失敗を直すものではない。

**この置き場を導出する行が全定義で一致することは掃引が検査する。** 導出は 3 本ある —— `hq:triage` と `hq:implement` の § Context の行 2 本と、上の作成の行 1 本である。前者 2 本は逐語で突き合わせる。3 本目は fenced block の中にあって形が違う（§ Context の行は最新のファイルを glob し、`mkdir` は作るだけである）ので逐語では比べられず、**使い捨ての home で block を実行してから § Context の行にどこを見るかを問う形で突き合わせる。** 3 本目を消す形は採れない —— fenced block は § Context が出した値を読めないので、作成の行は自分で導出する以外にない。中身が良いかどうかにも、書いた directive が当たったかどうかにも保証は無く、§ 設計原則 に従ってここに無いと書く。

**`HQ_HOME`（既定 `~/.hq`）が唯一の knob である。** telemetry と作業ファイルの両方がこれに従う —— 片方だけが従うと、knob を動かした時に home が黙って 2 つに割れ、2 つの母集団が 1 つとして読まれる。

**`HQ_HOME` は絶対パスでなければならず、相対値は拒否する。** 下の階層はすべてこの値から組み立てられるので、相対値だと呼び出し側の作業ディレクトリからの相対になる —— hook にとってそれは**作業中の repo** である。相対値を許すと、計画書と telemetry の両方が repo の中に落ちる。解決せず拒否するのは `record.sh` が先頭ゼロの duration を正規化せず拒否するのと同じ理由で、呼び出し側の誤りを呼び出し側で見せるためである。

**`HQ_HOME` も `HOME` も無い環境は、名前を言って拒否する。** 既定値は `$HOME/.hq` なので、`HOME` が無い環境では `set -u` が unbound variable で落とす —— 落ちる先は行番号であって、呼び出し側が設定できる変数ではない。しかも呼ぶ側は `2>/dev/null` で読む（module 定義の § Context 行がそうしている。detached HEAD で command 全体が壊れないため）ので、その行はどこにも出ず、**「detached HEAD」「repo でない」「相対 `HQ_HOME`」と同じ `unknown` に潰れる**。`/.hq` を既定にして黙って続けることはしない —— それは絶対パスなので上の検査を通り、home ごとファイルシステムの根に置く。この規則は導出（`lib.sh`）と telemetry（`record.sh`）の両方が持つ。

**`<repo-key>` は common git dir の絶対パス**を、先頭の `/` を落として `[A-Za-z0-9._-]` の外を `-` に畳んだものである。`--show-toplevel` は worktree ごとに違うが、common git dir は同じ clone の全 worktree で一致し、clone が違えば違う（実測）。したがって作業ファイルは **worktree ではなく branch について回る** —— 同じ branch を 2 つ目の worktree で開いても、既にある計画書がそこから見える。

**この鍵は単射ではない。** `/a/b/c` と `/a-b/c` は同じ鍵に潰れる。紛らわしい名前の clone を同じ機械に 2 つ置いた時にだけ起こる。塞ぐ機構は置かない —— hash は、パスが既に持っている一意性を、読めない鍵と 2 本目の fallback 連鎖と引き換えに買うことになる。性質として書くに留める。

**導出は `plugin/scripts/lib.sh` の `hq_repo_key` / `hq_task_dir` だけが持つ。** gate も module 定義も agent 定義もそこへ問い、自分では組み立てない。**呼ぶ側がそれぞれ場所を書き下す形では、どれか 1 つが外れても他は動き続け、外れたことに誰も気づかない。** 旧パスを名指す生きた定義が 1 つも無いことは sweep が常設で検査する。

**agent には caller が渡す。** subagent は plugin の script を呼べない（`${CLAUDE_PLUGIN_ROOT}` は shell の環境変数として存在しない）。`hq:review` は § Context で導出した出力先を起動 prompt に載せ、検証者はそれを与えられた事実として使う。

**渡したことは起動 gate が検査する。** 述語は 1 つで、**その branch の task dir の文字列が起動 payload に含まれるか**である。検証者にとってはそれが出力先そのもので、実装者にとっては渡される計画書のパスがそれを prefix として含むので、**1 つの述語が両方の起動を覆う** —— 検証者だけに絞ると、実装者側の同じ誤り（計画書のパスを渡し忘れる）が残る。gate は自分で組み立てず `lib.sh` に問う。**下流では代替できない** —— `findings-gate.sh` はファイルが無ければ何も言わずに終わるが、それは「書く場所を教えられなかった」と「指摘がゼロだった」の両方の正常な観測であり、区別が付くのは起動時だけである。

**この述語の保証にも境界があり、それを明記する。** 照合できない文字列のときは gate は黙る。`<repo-key>` は `[A-Za-z0-9._-]` に畳まれるが、`HQ_HOME` と branch 名は畳まれない —— `feat/日本語` も `"` を含む名も git 上は正当である（実測）。payload の encoder が非 ASCII を `\uXXXX` に変え、`"` と `\` を必ず escape する以上、そのような path は正しく貼られていても照合が外れ、**正しい launch を止める**。§ 入力の統治が本文照合について下したのと同じ判断を採る —— 誤検知は run を止め、沈黙は「その環境では保証が無い」で済む。導出自体が答えられないとき（detached HEAD・repo でない・home が無い・`lib.sh` が無い）も同様に黙る。

**module 単位の override 機構は置かない。1 つずつ、必要になった時点で足す。** 以前の設計は 10 種類前後を一括で持っていた。§ 入力の統治の「中身が無いうちから用意しない」に従い、その module に固有の注入が実際に必要になった時点で、その module の PR で決める —— この規定が現に適用されたのが上の表の `.hq/pr.md` であり、`hq:pr` の PR で決めた。`.hq/xcodebuild-config.md` も同じ形で足した —— 読み手は `hq:plan`（acceptance の bare build に Build Command を逐語で引く）と、その repo で `xcodebuild` を打つ者である。注入の一覧（`FILES`）には載せない —— acceptance は計画書の持ち物で、subagent は計画書から受け取る。検証者が計画書に無い build を要した実測が出たとき、`FILES` の 1 行として足す。**表に行が増えても機構が増えたことにはならない**。switch も分岐も無く、その module の定義が自分の Context でそのファイルを読むだけである。

**受け口の反映に保証は無い。** `.hq/pr.md` は層 2 に載らない（`hq:pr` は subagent を立てないので届かない）。本文がその形式に従っているかも決定可能でない —— 見出しを再定義する override と文体の指針だけの override はどちらも正当で、どちらの側からも述語が書けない。したがって pr-gate の述語には入れない。§ 設計原則の「移せないなら『この保証は無い』と明記する」に従って、ここに無いと書く。

## 5. 憲法

条文を選ぶ規則: 保証機構を持たない原則は書かない。

**第 1 条 — 質は外部残存で測る。**

loop の検出力についての主張は、loop の外にいる独立レビュアが後から見つけた欠陥と、クラス別に突き合わせて評価する。

保証機構: 出荷した PR ごとの外部指摘を区分する記録と、それを集計する script（§ 記録と評価指標）。区分の大半は「loop がどこで止まったか」を答え、指摘が真でなかったことを言う区分だけが別の軸になる。**区分の受理値は `record.sh` が持ち、この条文は書き写さない** —— § 記録と評価指標 が同じ値について定めている規定と同じで、書き写せば照合できない 2 本目の一覧になる。この記録は triage の質の実測も兼ねる。loop が検出しながら triage で落とした指摘が区分として切り出せるためで、棄却は「この指摘に consequence は無い」という主張であり、外部残存がその真偽を確かめるからである。

**第 2 条 — 機械が強制するのは決定可能な述語だけとし、行動を散文で指図する規範は置かない。**

保証機構: 各 gate の述語を red-on-revert で検査する。規範文書に行動の指図が混入した場合は、レビューでこの条文を引いて却下する。

**第 3 条 — 共有する情報は、提供されたことを機械が保証する。**

subagent が必要とする文脈は起動時に注入し、注入された事実と内容の新しさを機械が検査する。使い方は LLM に委ねる。

保証機構: 注入内容と現行ファイルの一致検査（§ 入力の統治）。

**第 4 条 — 検証は成果物の主張に向け、検証者は diff profile 別の実測収率で選ぶ。**

工程成果物の形式検査を検証と呼ばない。

保証機構: 検証者を選んだ記録に、参照した profile 別の収率を必ず書く。その選択が妥当だったかは、柱 B の記録が確かめる。

## 6. モジュール構成

基礎モジュール 7 つと、それらを束ねる orchestrator（`hq:loop`）で構成する。各モジュールは単独で機能する skill / command であり、loop はそれらを順に呼んでいるにすぎない。

| module | 役割 | loop |
|---|---|---|
| `hq:plan` | 計画の作成と計画 gate | 内 |
| `hq:implement` | 成果物を作る。subagent 起動時の層 2 の注入は自身で強制する | 内 |
| `hq:review` | 柱 A。成果物の主張の検証。層 2 の注入は検証者の起動時にも効く | 内 |
| `hq:triage` | findings の disposition（処置判定） | 内 |
| `hq:pr` | PR の作成と pr-gate。述語には **CHANGELOG が更新されていること**を含める。この文書の更新機会もここで作る | 内 |
| `hq:copilot` | PR についた外部レビューの指摘を取り込み、triage して対応する。**未実装**（§ 残っているもの） | **外** |
| `hq:archive` | merge 後の後片付けと、柱 B の記録 | 外 |

**表の外に、cycle に属さない command がある。** `hq:xcodebuild-config` は、Xcode の repo で build / run の command を利用者と 1 回決めて `.hq/` に書く（§ 作業ファイルの置き場）。loop は呼ばず、`module` の記録行も書かない —— 周回の費目に載せると、repo の初期設定が overhead/implement 比の分子に混ざる。読み手の側の規定は `hq:plan` の定義が持つ。

**gate は module が持つ。**
層 1 の述語検査と層 2 の注入保証は、各 module の契約の一部とする。loop には置かない。単独で起動しても loop 経由で起動しても、同じ保証が立つ。

**module の入力は、repo の状態（branch・diff・base）から導出できる。**
loop が作った成果物（計画書など）は、あれば精度が上がる補強情報であって、前提ではない。

**`hq:triage` は状態を持たない判定 module。**
入力はその branch の findings ファイルと計画書で、出力は指摘ごとの disposition と、その理由である。module 定義は `plugin/commands/triage.md` にあり、判定の手順と記録の書き方はそこが正典である。

- **判定は 2 つの述語で決め、重みが出口の強さを決める。** 述語は consequence の有無と、計画書の `## Editable surface`（fence）の内外である。帰結が無ければ `reject`、帰結があって fence の外なら `defer`、帰結があって fence の内なら `fix_now`。**「大きいから後で」は表に無い** —— fence の内で帰結があり、重みが low を超えるなら、直す以外の出口を作らない。棄却する前には、その判断を否定しうる検証を必ず 1 つ実行する。
- **重みが変えるのは、fence の内の low だけである。** high / medium は上のとおり `fix_now` で、出荷を止める。low は出荷を止めず、単独では修正 pass を起こさない —— 他に `fix_now` があればその pass に相乗りして `fix_now` になり、相乗り先が無ければ `defer` になる。限界費用がほぼゼロのもの（typo、1 行の書き換え）は、相乗り先の有無に関わらず直す。**この分岐が「大きいから後で」に戻らないのは、重みを付けるのが検証者であって triage ではないからである**（§ 出力の検証）—— 判定の側は重みを作れないので、費用を重みに翻訳する経路が無い。verdict の enum は変わらない。
- **計画書が無いときは `defer` を使用不可にし、帰結があれば `fix_now` に倒す。** 範囲を宣言していないなら、範囲外だと主張する根拠も無い。これは「module の入力は repo の状態から導出でき、計画書は前提ではない」を保つための規定でもある。
- **呼び出し点は 1 箇所である**（loop 内、review の直後、PR を作る前）。存在しない module を前提にした規定は置かない —— 呼び出し点を増やすのは、その呼び出し元が実在してからである。
- disposition は telemetry に記録される。これが第 1 条の「検出したが落とした」を照合する面になり、補助指標「柱 A の収率」の算出元でもある。
- **先送りの置き場は新設せず、記録の判定行がそのまま持つ。** 閉じる印は、識別子を `<branch>#<id>` に修飾した `fix_now` の行である。指摘の識別子は branch 内でしか一意でない（どの branch にも F1 がある）ので、閉じるのが別 branch の run である以上、閉じる行が元の branch を名指す必要がある。**読み方の規則は script が実装する** —— 同じ修飾済み識別子に後から `fix_now` の行が来ていれば閉じている、という形で、柱 B の実施記録が持つ `reviewed` の読み方と同じ型である。
- **`triage-gate.sh` が 2 副命令を持つ。** `check`（その branch の指摘が全部処置されたか）と `open`（開いている先送りの列挙）である。計画 gate が副命令を足す形（`surface`）を先に採っているが、そちらが持つ hook の顔はこれには無い。
- **層 2 の注入保証はこの module に無い。** 層 2 は subagent の起動に効く仕組みで、この module は subagent を起動しない（§ 入力の統治）。§ 設計原則の「移せないなら『この保証は無い』と明記する」に従って明記する。
- **修飾済みの識別子で閉じることにも保証は無い。** 閉じ忘れると、その先送りは `open` に載り続ける。誰かが直したことを機械が知る面は無く、これも § 設計原則に従って無いと書く。
- **`triage-gate.sh` が走ることにも保証は無い。** この script は `plugin/hooks/hooks.json` に入っていない（tool の呼び出しに割り込む必要が無いため外した。**登録されている側をここで数え上げない** —— 単一ソースは `hooks.json` であり、数を書き写せば hook を 1 つ足した日に黙って偽になる）。呼ぶのは `commands/triage.md` の散文だけであり、走らせないまま終えた run を機械が検出する面は無い。したがってこの module について、上の「gate は module が持つ」が定める層 1 の保証は**立っていない** —— 決定可能な述語を実装した script は在るが、それが実行されたことを確かめるものが無い。§ 設計原則に従って、無いと書く。

**`hq:pr` は、この文書がその変更で偽になっていないかを問う場所である。**
正典が実態と合っているかはテキストの検査では決まらない。決定可能なのは「plugin を触ったのに設計文書を触っていない」ところまでで、それ自体は正常な状態でもあるから、block はしない。PR を作る時点でその条件を見て、**更新の機会を作る**。この位置に置くのは、変更の全体が初めて 1 つの diff として見える時点だからである。それ以外の場所（掃引・commit ごとの hook）は、変更が揃う前に問うことになる。判定は diff profile が `code`（散文を 1 つも触っていない）かどうかで、これは `hq_diff_profile` が答える。

- **module 定義は `plugin/commands/pr.md` にあり、本文の材料と手順はそこが正典である。** 述語は `plugin/scripts/pr-gate.sh` が単一ソースで持つ —— **この文書は数も一覧も書き写さない**。書き写せば、照合できない 2 本目の一覧になる。上の表が CHANGELOG の条件を名指しているのは、この module をここに置いた目的の記述であって一覧ではない。
- **gate は PreToolUse の hook として `gh pr create` に割り込む。** したがって「gate が走ったこと」の保証は在り、そこが `hq:triage` と違う —— あちらは決定可能な述語を実装した script が在るだけで、実行されたことを確かめるものが無い。module 定義は同じ script の読む面を先に呼ぶが、それは手順であって保証ではない。
- **すべての条件は個別に fail open する。** 計画書の無い branch では計画を読む条件が、`CHANGELOG.md` を持たない repo ではその条件が、それぞれ黙る。**見られなかったことは、見て問題が無かったことと区別して報告する** —— ただし hook はそれで deny しない。この hook は plugin を入れた全 repo の全 Bash 呼び出しで評価され、誤検知は run を止めるからである（§ 作業ファイルの置き場 が起動 gate について下したのと同じ判断）。
- **本文の形式は repo 側が `.hq/pr.md` で決める**（§ 作業ファイルの置き場）。従っているかの保証は無い。
- **層 2 の注入保証はこの module に無い。** 層 2 は subagent の起動に効く仕組みで、この module は subagent を起動しない（§ 入力の統治）。§ 設計原則 の「移せないなら『この保証は無い』と明記する」に従って明記する。

**`hq:copilot` を loop に含めないのは、柱 B の独立性を保つためである。**
loop が外部レビューを呼んでその結果を読む構成にすると、そのレビュアは loop の外ではなくなり、第 1 条の測定手段を失う。名前は GitHub Copilot に由来するが、**この module は特定のサービス専用ではない**。扱うのは PR についた外部レビューの指摘全般であり、出所（ユーザのレビュー、ユーザが起動した外部レビューツール、Copilot）は問わない。

- **この module はまだ無い**（§ 残っているもの）。以下の流れは作るときの出発点であって、現在の呼び出し関係ではない —— 今の `hq:triage` の呼び出し点は 1 箇所である（上）。内部の流れは、PR コメントを読む → 決まった形式の findings に変換する → `hq:triage` を呼ぶ → disposition に従って対応する（fix now は micro-fix、reject は根拠を添えて PR に返信、defer は記録して返信）。
- この module 自身は外部レビューを起動しない。起動はユーザが行い、module はその結果を取り込む。
- 外部指摘への対応は、柱 B の測定に影響しない。merge 前に直しても、archive の残存記録からは消えない。分類の問いが「loop は PR を作る前にこれを検出していたか」だからである。対応と測定は、同じ記録を読む別々の判断として分ける。

**`hq:archive` は merge の後に走る、柱 B の書き手と run の終端である。**
module 定義は `plugin/commands/archive.md` にあり、決定可能な述語と削除は `plugin/scripts/archive.sh` が持つ —— `missing`（base の merge commit の件名から PR 番号を導出し、telemetry に residual 行の無いものを列挙する。gh にも network にも出ない）と `cleanup`（その branch が残したものの削除。作業ディレクトリと local branch の 2 つを、それぞれ独立に扱う）の 2 面である。gate と呼ばないのは、検査だけでなく削除という操作を持つためである。保証の所在は次のとおりで、無いものは § 設計原則に従って無いと書く。

- **hook は持たない。** merge は forge の上で起き、tool の呼び出しに割り込む面が無い。存在しない呼び出し点を前提にした規定は置かない（`hq:triage` の先例）。
- **実行されたことの保証も無い。** 呼ぶのは module 定義の散文と人であり、走らせないまま終えた run を機械が検出する面は無い。忘れれば柱 B の分母が黙って欠ける —— `missing` の顔は、その欠けを次の実行が拾うために在る。欠けは検出できないが、閉じられる。
- **`cleanup` が消すのは 2 つで、独立に扱う。** 作業ディレクトリと **local branch** である。どちらか一方だけが在る状態は普通に起きる（merge で local ref が消えた branch には directory だけが残り、前の実行で directory を消した branch には branch だけが残る）ので、一方の不在をもう一方の不在と見なさない。**remote branch には触らない** —— 削除は merge のときに forge が行うことで、手元の道具が戻せない ref を消しにいかない。
- **`cleanup` は不可逆であり、決められないものは消さない。拒否の一覧と数は `archive.sh` が単一ソースとして持ち、この文書は書き写さない**（`hq:pr` の述語と同じ理由 —— 書き写せば照合できない 2 本目の一覧になり、経路を 1 つ足した日に黙って古くなる。実際この項は一度そうなった）。ここに書くのは規準である —— base に merge 済みだと示せないもの、パスの物理的な解決先を確かめられないものは、疑いを残したまま消さない。**base branch 自身だけは merged 判定より前で拒む必要がある** —— tip が自分自身の ancestor なので判定では捕まらず、その作業ディレクトリは merge 後の記録の run_id を持つ生きた state だからである（比較は base の解決結果に対して行う）。**拒否は「何も消していない」と同義ではない。** 2 つの削除は独立していて、後の側（local branch）の拒否は前の側（作業ディレクトリ）が消えた後にも起きる —— その branch を別の worktree が checkout していて git が削除を拒む場合である。したがって拒否を報告する側は、script が stdout に出した「何を消したか」を併せて読む。消える directory は run_id の寿命の終端である（§ 記録と評価指標）。削除がこの script に在るのは、module 定義の fenced block はテストスイートが実行するため、そこに破壊的な command を置けないからでもある —— この顔が module の唯一の削除経路になる。
- **自分が居る branch を消すときは、削除の前に base を checkout する。** checkout できるのは local branch だけである —— `origin/<base>` を checkout すると detached HEAD になり、次の run の `hq_task_dir` が拒否する状態を作る。checkout を削除の前に置くのは、これがこの working tree の未 commit の変更に拒まれうる唯一の段だからで、そこで止まった run は何も消していない（上の、別の worktree が握った branch の削除が拒まれる経路は、これとは別の段である）。

**loop が持つのは、呼び出し順の管理と計測だけである。**
計測する内容は「何が実行されたか」と「所要時間」。module の境界が、そのまま計測の境界になる。module 定義は `plugin/commands/loop.md` にあり、呼び出し順と相談の条件はそこが正典である。**入口の導出だけは script が持つ**（`plugin/scripts/loop-state.sh`）—— 観測から module 名 1 つへの写像は決定可能な述語であり、散文に置くと照合する機械が 1 つも無いためである。

- **入口は状態の導出で決め、観測はローカルに閉じる。** 何をどう見るかと、そこから module 名 1 つをどう決めるかは `loop-state.sh` が単一ソースとして持ち、この文書も module 定義もその表を書き写さない（下の相談条件と同じ理由）。ここに書くのは判断だけである —— **観測はこのマシンの上に閉じ、forge には問い合わせない。** PR が既に在るかは `hq:pr` が自分で見るし、run の入口を network の応答に依存させない。**導出そのものが答えを出せなかったときは、module と同じく止まって報告する** —— script は導出できなかった値を `unknown` として出し、exit 2 で止まる。残った曖昧さは早い側の module に倒す —— 早すぎる呼び出しは「やることが無い」と返る 1 pass の損で、遅すぎる呼び出しは誰も戻ってこない工程を飛ばす。**module 定義が表の写しを併記していないことの保証は無い。** 掃引が見るのは `loop-state.sh` を呼んでいることと、置き換えた gate を直接呼んでいないことだけで、散文が写しを持たないことは決定可能な述語にならない。§ 設計原則 に従って、無いと書く。
- **ユーザに相談する条件は module 定義が単一ソースとして持ち、この文書は数も一覧も書き写さない。** 書き写せば、条件を 1 つ足した日に、照合できない 2 本目が黙って古くなる。ここに書くのは選ぶ規準である —— **次に何をするかの選択が loop の持ち物でないものだけを相談点にする。** 判断の主が module 側にも計画 gate にも無い状態が、そのまま条件になる。中でも、module の報告がその module の定義で「user の判断」と定められている事柄を運んできたときに止める規定が、「loop は、実装者が計画書の誤りを報告してきたときを定義していない」として記録された穴への答えである。**周回数を条件に使うものについては、閾値は仮置きで、根拠となる実測はまだ無い** —— 値は module 定義が持ち、run が貯まった時点で置き直す。
- **`hq:pr` は聞かずに呼ぶ。** 呼ぶ条件そのものは module 定義が持つ。ここに承認を置かない理由は 2 つ —— 人の承認は計画 gate が既に取っており、PR を出してよいかの述語は `pr-gate.sh` が持つ。終端に停止点を足すと、loop が消すはずの人待ちが最後に戻る。**ただし計画 gate が取った承認は「満たすべき成果」と「触ってよい範囲」までで、設計は含まない** —— 設計は `hq:implement` の中で人が居ないまま決まる。**これは途中で変わった点である。**以前は計画が作業項目まで書いていたので、承認の対象に「何を作るか」が入っていた。今それを補うのは、実装者の返答と PR 本文（設計と却下した案がそこに載る）と柱 A であって、loop の中に停止点は戻さない。
- **loop は telemetry の行を書かない。** 各 module が自分の pass を記録し、計測の境界は module の境界である（§ 記録と評価指標）。最終報告が集計するのは、その session で各 module が記録した `duration_s` であって、loop が自分で取った時計ではない。envelope の行（loop の起動から報告までの wall-clock）を置かないのは、計画 gate と相談のユーザ待ちで上に無制限にぶれるためで、`hq:review` が wall-clock を捨てたのと同じ判断である。
- **したがって縫い目は未計測である。** loop 自身の導出・読み・報告に要した時間はどの行にも入らず、どこでも推定しない。§ 設計原則 に従って、無いと書く。
- **実行されたこと・呼び出しの順序・収束の判定のいずれにも保証は無い。** 層 1 の述語も層 2 の注入も各 module が持ち、単独で起動しても loop 経由でも同じに立つ（上の「gate は module が持つ」）。**この頁のとおりに呼ばれたことを確かめる面はどこにも無い** —— loop を飛ばして module を手で打った run と、loop が順に呼んだ run は、記録の上で区別が付かない。相談を飛ばしたことも、module 定義が置いた周回数の閾値で止まらなかったことも同じである。§ 設計原則 に従って、無いと書く。

**判断の記録は、ユーザが読む判断に限定する。**
対象は計画 gate、ユーザへの相談、最終報告の 3 つ。それ以外の判断は telemetry の 1 行として残す。

**fix の経路。**
triage が fix now と判定したものは `hq:implement` に戻す（micro-fix）。この経路が時間を節約し続けているかは、補助指標の修正の限界コスト比が確かめる。

- **1 周分の directive は 1 回の micro pass にまとめる。** triage は判定した directive を run の作業ディレクトリの `directives/` に 1 ファイルとして書き、`hq:implement` にはそのパスを渡す（§ 作業ファイルの置き場）。まとめる理由は、micro route が「全 directive を当ててから `## Floor` を回す」ので、1 pass = 1 件だと合格判定が件数の分だけ回るからである。
- **まとめると検査が純減するので、その分を micro route の側に足す。** 合格判定が 1 回に減る以上、fresh route が項目ごとに持っている「最も狭い検査」に相当する段が micro route にも要る。実装は agent 定義（`plugin/agents/implementer.md`）が持つ。
- **1 回の pass が複数件を運ぶので、記録の 1 行の意味が変わる。** 母集団の意味の変化と、それをどう読むかは § 記録と評価指標 が持つ。

### 6.1 計画の戦略 — `hq:plan`

module 定義は `plugin/commands/plan.md` にあり、計画書の形式契約（節・タグ・表の形）はそこが唯一の正典である。ここに書くのは、その形を選んだ理由と、保証がどこにあるかである。

**この module が決めるのは 3 つだけである。** 満たすべき成果とその確かめ方（`## Requirements`）、調査で分かった事実（`## Notes`）、触ってよい既存ファイルの集合（`## Editable surface`）。**設計は含まれない** —— どう作るかは実装者が決める。

**なぜ設計を計画から外したか。** 以前は計画が作業項目を commit 単位で並べ、そこに何を作るかを書いていた。その指定は、実装者がより良い形を知っていたときに破られる。破ってよいなら、その粒度で書いた労力は実装者が同意した部分にしか効かない。破ってはいけないなら、劣った設計がそのまま出荷される。どちらに倒しても損をする。**実測でも確かめた** —— 出荷済みのある変更で、計画が名指した関数は 9 本、実際に出荷された module の export は 20 個で、伏せ字の作り方も更新の流れをどの層に置くかも計画とは別の形になっており、計画の指定のほうが劣っていた。

**手順の骨格は、要件の合意 → 俯瞰 → 作成 → 読み返し → 提示 → 書き込み、である。** 人が必ず入るのは 2 箇所 —— 何が満たされていれば良いかを詰める合意と、これで進めるかを問う gate である。**合意が調査より前に来ることに意味がある** —— 何を満たすかが決まっていなければ、何が影響範囲かも決まらない。以前は逆順で、これは欠陥だった。

**成果物の節は 5 つで、任意のものは無い。** 節の名前は module 定義（`plugin/commands/plan.md`）が単一ソースとして持ち、計画 gate の実装と一致することはテストが検査する。**下の表が名前を再掲するのは、それぞれが何のためにあるかを説明できないためで、この再掲は機械が照合している**（`.claude/scripts/docs-check.sh`）。役割で分けると次のようになる。

| 群 | 節 | 何のためにあるか |
|---|---|---|
| 導入 | Summary | 何をしようとしているかを、対象リポジトリの語彙だけで 3〜5 行。plugin の語彙を持ち込まない。**これだけ読んで分かることが要件である** |
| 判定 | Requirements | 満たすべき成果と、それを誰がどう確かめるかを 1 行に並べた表。**2 つの箇条書きに分けない** —— 対応が必要な 2 本の一覧は、黙って食い違う形そのものである |
| 根拠 | Notes | 調査で分かった事実。制約・波及・地雷・触らないと決めたもの（理由付き）。**設計の決定ではなく事実を書く** —— 設計を変えても真であり続けるものだけが入る |
| 決定 | Editable surface | 触ってよいパスの集合。計画が宣言するのは調査で見えた既存ファイルで、新しく作るファイルは設計の産物なので実装者が理由とともに足す |
| 下限 | Floor | どんな実装でも通るべき機械の検査。ビルド・型・lint・テスト。**判定ではない** |

**要件と作業項目の見分け方は 1 つである。** 設計を別の形に変えたとき、その文が生き残るか。「トークンが失効する前に自動で延長される」は生き残る。「更新要否の判定を token-store に置く」は書き換わる。後者は計画に入れない。

**確かめ方は 2 種類あり、どちらも書いた本人の言い分ではない。** `[manual]` は人が 1 つの観測を見る。`[review]` は柱 A の検証者が、作られたコードのどこでその成果が満たされているかを辿る。辿れない行は finding になる。**「実装した本人が満たしたと言う」は確かめ方として認めない** —— 書いた側と検証する側を分けることが柱 A の定義そのものだからである。

**分ける軸は「誰が見るのが自然か」ではなく「ここで機械が確かめられるか」である。** テストで主張できる成果は `[review]` に倒し、実装者がそのテストを書き、検証者はテストの名前ではなく中身を行に対して読む。**逆にすると 2 通りに壊れる** —— テストが既に覆っている成果が PR 本文に「人がまだ確かめていないこと」として残り続けるか、誰も fixture を作らない作業が人に渡されるかである。これは実地で出た欠陥で、`[manual]` と `[review]` の 2 つしか無いために「実装者が書くテストが確かめる」の置き場が無く、書き手が `[manual]` に倒したことによる。**タグを 3 つ目にせず `[review]` の定義を広げたのは、検証者の仕事（実装のどこで満たされているかを辿る）がテストを読むことをそのまま含むためである。**

**`[primary]` の指名は廃止した。** 判定の 1 本を強くするには実装の形を知っている必要があり、その形は実装者のものになった。計画の時点で「変更前に赤い」を確かめる手順も、同じ理由で成立しない。**その手順が守っていた性質は捨てていない** —— 検査を足したら、それを満たすコードを書く前に走らせて落ちることを見る、という規定は実装者側に残り、記録は `checks.md` が持ち、検証者がその破り方を複製して確かめる。

**「計画したことをやったか」は、強さの違う 3 段で答える。** 混同すると、答えている問いが変わる。

| 段 | 答える問い | 誰の言い分か |
|---|---|---|
| `## Plan` の checkbox | やったつもりか | **実装者の自己申告。検証ではない。** PR gate は未チェックが無いことしか数えない。この節は計画には無く、実装者が設計を終えた時点で書く |
| `## Editable surface` と diff の集合差 | 宣言したものを触ったか / 宣言していないものを触っていないか | 機械。実際の diff から導くので自己申告に依存しない |
| `## Requirements` の `[review]` 行 | 変更が本来の目的を果たしたか | 柱 A の検証者。実装のどこで満たされているかを辿る |

**保証の所在。** 層 1 が持つもの、柱 A に委ねるもの、どちらも無いものを分けて書く。無いものを書くのは § 設計原則の規定による。

| 事柄 | 保証 |
|---|---|
| 計画書の形（節・表の行・タグ・下限が実行可能なコマンドを名指すこと） | **層 1。** 書き込みに割り込む gate が検査し、合わなければ差し戻す |
| 計画書が、今いる branch の場所に書かれること | **層 1。** 別の branch の場所に書かれたら止める |
| 宣言した触る箇所と、実際の diff の一致（宣言に無いものを触っていないか） | **層 1。** commit のたびに計画 gate の hook が集合差を取り、宣言に無いパスを名指す。commit されていない変更は見えない |
| 実装者が作業項目を書いたこと | **層 1。** PR gate が `## Plan` 節の不在を違反として数える —— その節は設計を終えた実装者が書くので、無いことは設計まで到達しなかったことを意味する |
| gate が実際に何回止めたか | **層 1。** 拒否のたびに記録 script が 1 行書く（§ 記録と評価指標）。**止めたものは diff に現れない**ので、これが無いと「効いている gate」と「一度も火を噴かない gate」を後から区別できない |
| 要件が実際に満たされたか | **柱 A と人。** `[review]` 行は検証者が辿り、`[manual]` 行は人が確かめる |
| 要件の妥当性（そもそもその成果で良いのか） | **人。** 決定可能な述語にならない。提示の gate が唯一の面である |
| `## Notes` が調査を正しく写しているか | **無い。** 調査の結果と本文の一致を機械で見る手段が無い |
| ユーザへの提示と go / stop を飛ばさないこと | **無い。** 飛ばしたことに気づける面が作れない |
| 起動時の注入（層 2） | **無い。** 層 2 は subagent の起動に効く仕組みで、この module は対話のため subagent を立てられない（§ 入力の統治） |
| 本文の数が、それを出す command として併記されていること | **無い。** 計画書は repo の外に在り diff に現れないので、検証者も外部レビューも読まない |

**この形は測っていない。** 採用の根拠は否定形である —— 逆方向（作業項目の粒度を上げ、署名と振る舞いの例と状態の列挙まで書く）を 3 周測り、曖昧な計画にあった「決めないと 1 行も書けない」6 件のうち 4 件は粒度で閉じたものの、閉じた先で計画の指定が実装より劣る箇所が生まれ、最後に残った穴の主因は規則の不足ではなく規則への不遵守だった。**同じ失敗クラスに散文の条項を足す方向が効かないことは、この 3 周が示している。**

## 7. 記録と評価指標 — telemetry

**telemetry は schema 3 に切り替える。**

集約先は 1 ファイル（`~/.hq/stream.jsonl`）で、1 行が 1 件の記録。`schema` の値が、以前の世代の記録（schema 2）とこの plugin の記録を切り分ける印になる。schema 2 はもう増えない。読み取り専用の過去データとして凍結し、両方をまたいで比較するときだけ双方を読める reader で扱う。

**実装の唯一の正典は `plugin/scripts/record.sh` である。** 項目の名前・必須と任意の別・enum の受理値は、その script だけが持つ。**この文書はそれを書き写さない** —— 書き写せば、照合できない 2 本目の一覧になる。値を知りたいときは `record.sh --help` を引く。

設計として決めてあるのは次の 4 点である。

- **1 行が 1 件で、追記だけを行い、既存の行は書き換えない。** 状態が変わったときは新しい行を足し、読むときの規則で解決する。
- **全行が共通の外枠を持つ。** いつ・どの repo の・どの branch の・どのサイクルの出来事かが、どの行からも読める。サイクルの識別子は 1 サイクルに 1 つとする。
- **記録の種類は 4 つで、書く主体が種類ごとに決まっている。** module の実行（各 module が書く）、指摘の処置（`hq:triage`）、外部残存（`hq:archive`）、gate の拒否（gate 自身）である。
- **gate の拒否だけは、書く主体が module ではない。** **gate が止めたものは diff に現れない** —— 拒否された commit は起きなかったので、後から見ると「毎回止めている gate」と「一度も火を噴かない gate」の見分けが付かない。この行だけがその区別を持つ。拒否と「検査できなかった」を別の値にしてあるのは、検査できなかった gate を通過と畳むと、検査が動かない環境のすべての run が正常に見えるためである。**記録の失敗が拒否を取り消すことは無い** —— telemetry が壊れたので悪い commit を通す、はどちらの向きから見ても割に合わない。
- **`reason` は先送りの行でだけ必須で、記録 script が拒否する。** 先送りは、指摘が真のまま何も直っていない唯一の処置であり、この行が「何が成り立てば直せるのか」の唯一の記録になる。開いている先送りの列挙（`triage-gate.sh open`）はこの欄を読み返す。**書く中身が良いかどうかは決定可能でないので、そこに保証は無い**（module 定義が散文で扱う）。

`route`（`hq:implement` の入口の区別）を enum にしてあるのは、補助指標の修正の限界コスト比がこの経路ごとの所要時間の比だからである。**同じ経路に 2 通りの綴りが混ざると母集団が黙って割れる** —— 行は整形式のままなので下流は気づかない。

**`micro` の行は、その pass が渡された directive の件数を併せ持つ。** 1 pass = 1 件だった頃は所要時間がそのまま 1 件あたりの費用として読めたが、1 周分をまとめて渡す以上、正規化する材料が行の側に無いと読めない —— 件数の無い行は整形式のまま、1 件の費用として読まれ続ける。これも `route` を enum にしたのと同じ理由（母集団が黙って割れる／黙って意味を変える）である。**鍵の名前・受理値・どの行が受け付けるかは `record.sh` が持ち、この文書は書き写さない。**

**`duration_s` が何を測っているかは module によって少し違い、`hq:review` は途中で変えた。**
現在の `hq:review` の行は harness が返す**検証者の実行時間**であり、呼び出し側の手順
（文脈の取得・起動・記録）を含まない。時計の引き算をやめたのは、背景で起動したときに
「記録を書いた時刻」が待ち時間を含んで無制限に上振れするためで、**一定方向に少し低い値
のほうが、任意に高くなりうる値より読める**という判断による。

**切り替え点を記す。PR #255 より前の `review` の行 3 本（694 / 936 / 933 秒）は wall-clock
で、検証者の実行時間より 30.3 / 34.1 / 47.0 秒（3.6〜5.0%）大きい。** `schema` は 3 の
ままにした —— schema の役目は世代の違う母集団を切ることで、module 1 つの意味の差に
使うと過去の全行が読めなくなる。差は 5% 未満なので、混ぜて読んでよい。混ぜたくない
用途では、この 3 本を上の実測値で補正する。

**`run_id` の意味も途中で変えた。切り替え点を記す。**
それまでの実装は `HQ_RUN_ID` が未設定なら呼び出しのたびに識別子を組み立てており、
`HQ_RUN_ID` を設定するものは plugin に 1 つも無かった。したがって「1 サイクルに 1 つ」は
規定だけがあって実装が無く、行は整形式のまま群が 1 行ずつに割れていた。**切り替えたのは
2026-08-16 で、それより前に記録された schema 3 の行が切り替え前である。** 以後は branch
ごとに 1 つで、`hq_run_id` が run の作業ディレクトリに置いたファイルがその値を持つ。

過去の行は書き換えない（上の 4 点の 1 つ目）。読むときの規則は 2 つ。**切り替え前の行は
run で束ねられない**ので、run 単位の集計 —— overhead/implement 比と run の所要時間 ——
は切り替え後の行だけを母集団にする。行がどちら側かは記録時刻で決まる。`schema` は 3 の
ままにした —— 理由は `duration_s` のときと同じで、schema の役目は世代の違う母集団を
切ることであり、項目 1 つの意味の差に使うと過去の全行が読めなくなる。

**`route=micro` の 1 行が数える件数も途中で変えた。切り替え点を記す。**
それまでは directive 1 本につき `hq:implement` を 1 回起動していたので、micro の行 1 本が
修正 1 件の費用だった。1 周分の directive を 1 回の pass にまとめる形に変えたので、以後の
micro の行は 1 行が N 件である。**両側を分けるのは記録時刻ではなく、行が件数を持つかどうか
である** —— 件数を要求する記録 script と、1 周分を 1 pass にまとめる module 定義は同じ
plugin の版で出るので、件数を持たない行は、いつ書かれたものであれ 1 pass = 1 directive の
規約で動いている install が書いたものである。したがって**件数を持たない `route=micro` の行が
切り替え前であり、持つ行が切り替え後である。** 過去の行は書き換えない（上の 4 点の 1 つ目）。読むときの
規則は 1 つ —— **1 件あたりの費用を出すときは、件数を持つ行はその値で割り、持たない行は 1 件
として読む。** `schema` は 3 のままにした —— 理由は `duration_s` のときと同じで、項目 1 つの
意味の差に使うと過去の全行が読めなくなる。

**該当する行を数える。** この文を書いた時点で、集約先の `route=micro` の行は 68 本あり、
**その全部が件数を持たない**（= 全部が切り替え前）。内訳はこの repository が 45 本、plugin を
導入した別の repository が 23 本である。**この集合はまだ閉じていない** —— 切り替え前の版の
plugin が入ったままの repository は、更新するまで件数を持たない micro の行を書き続ける。
`false_positive` の項が名指す 1 行と違い、ここで数えた 68 本は「これ以上増えない集合」では
ないので、監査するときは件数の有無で選び直す。

**日付では両側を分けられないので、分けない。** 切り替えの実装が入ったのは 2026-08-20 だが、
その日には切り替え前の pass が書いた行も在る —— この repository の 45 本のうち 1 本が
2026-08-20T00:57:57Z（`duration_s` 454）で、これは
1 pass = 1 件の規約で書かれた行である。日付を境界にすると、この 454 秒が N 件分の費用として
割られる。件数の有無で切れば、この誤りは起こらない。

**偽陽性の区分が無かった時期がある。切り替え点を記す。**
`false_positive` を受理値に足したのは 2026-08-19 であり、それより前に記録された
外部残存の行は、偽陽性を表せない。**該当するのは 1 行だけである** —— PR #276 の
`residual`（`reviewer=codex-review`、`state=reviewed`、`logic:out_of_scope` 1 件、
記録時刻 2026-08-19T10:32:43Z）。この指摘は宣言クラス外だったのではなく、指摘された
欠陥が実在しなかった。**読むときは、この行の 1 件を偽陽性として扱う** —— すなわち
「宣言クラス外の指摘は検出範囲を広げる候補として読む」の対象にせず、外部残存の母集団
から除く。行を書き換えないのは上の 4 点の 1 つ目による。この 1 件より後の偽陽性は、
区分そのもので記録される。

**サイクルの境界は branch の寿命とする。** 出荷後に外部レビュアの指摘へ対応する分まで
同じサイクルに入る —— PR を出す時点で識別子を回すと、同じ PR の作業が 2 つの群に割れ、
overhead/implement 比の分子と分母が別の母集団になる。**識別子は run の作業ディレクトリと寿命を共にする。**
そのディレクトリが在るかぎり、同じ branch の記録は同じ識別子に入り、消えれば次の記録が
新しい識別子を作る。消すのは `hq:archive` の後片付けである。

`residual` は「外部レビューを実施したか」を状態として持ち、指摘の件数と組み合わせて読む。実施して指摘あり、実施して指摘ゼロ、未実施を区別するためである。区分の大半は第 1 条の言う「loop がどこで止まったか」に対応し、指摘が真でなかったことを言う区分だけが別の軸になる。**状態と区分の受理値は `record.sh` が持ち、この文書は書き写さない** —— 受理値を 1 つ足した日に、書き写した側だけが黙って古くなる。

**主な指標は 2 つ。**

- **質 = 外部残存。** 出荷した PR ごとの外部指摘を、クラス別に並べた系列。ゼロが目標ではなく、宣言クラス内の残存がゼロであることが目標である。宣言クラス外の指摘は、検出範囲を広げる候補として読む。**区分が `false_positive` の指摘 1 件を母集団から除く。** 他の区分が「loop がどこで止まったか」を答えるのに対し、これは指摘が真でなかったという別の軸であり、loop の検出力について何も言わない。除くのは行ではなく指摘 1 件である —— 区分は `residual` の行そのものではなく、その行が持つ指摘の 1 つずつに付くので、同じ行に並ぶ他の指摘は母集団に残る。
- **時間 = overhead/implement 比。** implement 以外の所要時間 ÷ implement の所要時間。`module` の記録を集計して算出する。数値目標は置かず、実測が数 run 貯まってから根拠を持って置く。

**補助の指標は 3 つ。** 維持するかどうかの基準は、読んだ結果が流れ込む判断があるかどうかとする。この基準を満たさない指標は置かない。

| 指標 | 定義 | 算出元 | 流れ込む判断 |
|---|---|---|---|
| 柱 A の収率 | 柱 A が出し、triage が棄却しなかった findings の件数 | `source=review` の `disposition` 行。profile 別に見るときは同じ branch の `module` 行と突き合わせる | 検証者を選ぶ根拠（第 4 条）。問うのは「重大なものを捕まえたか」ではなく「実害のあるものを捕まえたか」である |
| run の所要時間 | 1 サイクルの所要時間 | `module` 行の集計 | 分布を見る。主計器は overhead/implement 比で、これはその補助 |
| 修正の限界コスト比 | micro 経路と通常経路の、修正 1 件あたりの所要時間の比 | `module` 行の `route` と、micro の行が持つ directive の件数 | micro-fix が時間資産であり続けるかの確認 |

指標に番号は付けない。番号は定義を運ばないので、参照した先で何を指しているかが読めなくなる。

## 8. 残っているもの

**どの module が在るかは `ls plugin/commands/` が答える。**ここに書くのは、まだ無いものと、それが無い理由である。

**`hq:copilot` は作っていない。** 表（§ モジュール構成）に載っているのは、それが cycle の一部として設計されているからであって、実装が在るからではない。止まっている理由は 1 つ —— **PR に付いた外部指摘を、どの形でどこに置くかが決まっていない。**柱 A の findings は形式が決まっていて `findings-gate.sh` が検査するが、外部指摘はその形をしていない。同じ形に寄せるのか、別の入口を作るのかを決めないと、`hq:triage` が読む面が 2 種類になる。

**投入順は使い切った。** 記録 script から loop まで、module は作った端から構築作業に使う順で入れた。その順序が持っていた forward の内容はもう無い。

**この repository は、自分の cycle を自分で回していない。** 以前は module を作った端から構築作業に使っていた（incremental dogfood）。やめたので、次の 2 つが立たなくなっている。**書いておくのは § 設計原則 の規定による。**

- **実行の面（§ 出力の検証）が、この repository では作られない。** 定義が正しくても記述どおりに動くとは限らない、という面は、module を実際に使うことでしか現れない。他の repository で使えば現れるが、この repository の変更に対しては現れない。
- **柱 B の記録が、この repository の PR については取れない。** 外部残存の category は「loop がどこで止めたか」を答える欄で、loop を回していない branch に `missed` を記録すると、走っていない loop の取りこぼしとして数えられる。**記録しないのが正しく、記録が無いことは柱 A の成績ではない。**
